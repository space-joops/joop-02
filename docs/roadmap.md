# 로드맵 — 마일스톤 M0~M7

이 문서는 **무엇을 어떤 순서로 만들지**를 정의합니다. 기획 내용(왜 만드는지)은 [`../CLAUDE.md`](../CLAUDE.md), 기술 선택의 근거는 [`decisions.md`](./decisions.md), 각 단계의 학습 주제는 [`growth-roadmap.md`](./growth-roadmap.md)를 참고하세요.

## 현재 위치

| 항목 | 값 |
| --- | --- |
| 진행 중인 마일스톤 | **M2 완료** (실기기 확인만 남음) |
| 레포 상태 | 홈 → 아케이드 → 결과 → 프로필까지 이어지고 **기록이 누적됨** |
| 다음 작업 | **M3 — 캐릭터 비주얼 고도화** |

> 마일스톤을 완료하거나 착수할 때마다 이 표를 갱신합니다.

## 전체 흐름

```
M0 기반  →  M1 아케이드 코어  →  M2 누적 실적  →  M3 캐릭터 비주얼
                                      ↓
                          M4 지구 레이어 온보딩  →  M5 통신 시간 시스템
                                      ↓
                            M6 성격 유형  →  M7 서버 저장 & 바이럴
```

M0~M3은 **"플레이 가능한 하나의 세로 슬라이스"** 를 만드는 구간입니다. 이 네 단계가 끝나면 홈 → 청소 → 실적 확인까지 실제로 손에 잡히는 게임이 됩니다. M4 이후는 그 위에 세계관 레이어를 얹는 확장 구간입니다.

## M0 — 프로젝트 기반 ✅

**목표**: 코드를 쓸 수 있는 상태를 만든다. 이후 모든 마일스톤이 딛고 설 바닥.

**범위**

- ~~Next.js 14~~ **Next.js 16** App Router + React 19 + TypeScript 스캐폴딩 (npm) — 버전 변경 경위는 [`decisions.md`](./decisions.md) ADR-008
- 모바일 세로 화면 고정 레이아웃 셸 (`app/layout.tsx`) — 뷰포트 설정, safe-area 대응, 가로 방향 안내
- CSS Modules + 디자인 토큰(CSS 변수): 색상·간격·타이포·z-index를 `app/globals.css`의 `:root`에 정의
  - 디자인 작업과 병렬로 진행되어 한때 토큰이 두 벌이었습니다. **ADR-010에서 한 벌로 통합**되었고 정본은 `app/globals.css` 입니다
- ESLint + Prettier 설정
- Vitest 설정 (게임 로직 단위 테스트용, jsdom 환경)
- GitHub Actions CI: `format:check` → `lint` → `typecheck` → `test` → `build`
- 홈 화면 (`app/page.tsx`): "청소하러 가기" / "프로필 보기" 진입점
- `.gitignore`, `README.md`

**완료 기준 (DoD)**

- [x] `npm run dev`로 홈 화면이 뜨고, 모바일 세로 뷰포트에서 레이아웃이 깨지지 않는다 — iPhone 14 Pro(393×852) 및 좁은 가로(852×393) 렌더 확인
- [x] `npm run lint`, `npm run test`, `npm run build`가 모두 로컬에서 통과한다
- [x] 위 명령이 GitHub Actions에서도 통과한다
- [x] 색상·간격 값이 컴포넌트에 하드코딩되지 않고 CSS 변수를 거친다
- [x] **Vercel에 배포된다** — 레포가 연결되어 `main` 커밋마다 Production 배포가 생성되고, PR마다 Preview 배포가 붙는다. M0 머지 커밋의 Production 배포 상태는 `success`
- [ ] 실제 휴대폰에서 열어 확인 — **사용자 확인 필요**

**선행 조건**: 없음

**남은 것**: 실기기에서 배포본을 열어보는 것. 개발 환경의 네트워크 정책이 `vercel.app` 접근을 막아(게이트웨이 403) 에이전트가 직접 확인할 수 없다. 브라우저 자동화로 확인한 것은 로컬 dev 서버까지다.

## M1 — 아케이드 모드 코어 ✅

**목표**: 60초 동안 실제로 재미있게 조작되는 청소 플레이를 만든다. 이 프로젝트에서 기술적으로 가장 어려운 구간.

**범위**

- `requestAnimationFrame` 기반 게임 루프 + delta time 정규화 (프레임률과 무관한 이동 속도)
- 가상 조이스틱 (`components/Joystick.tsx`): 포인터 이벤트 기반, 터치·마우스 동시 지원
- 관성 이동: 조이스틱 입력을 가속도로 받고 속도에 감쇠 적용, 화면 경계 처리
- 쓰레기 스폰 시스템: 종류(먹을 것 / 위험 파편), 크기, 질량(kg), 스폰 주기
- 자동 흡수: 충돌 판정(원-원 거리 비교), 별도 액션 버튼 없음
- 성장: 흡수한 질량에 따라 줍스 반지름 증가 → 판정 범위·흡수 가능 크기 상한 확장
- 위험 파편 패널티: 크기·점수 감소만. **게임 오버 없음**
- 시각 구분: 먹을 것 = 따뜻한 색/둥근 형태, 위험 = 경고색/뾰족한 형태
- 세션 구조: 60초 타이머 → 신호 끊김 연출 → 성과 요약 화면

> 오브젝트·배경·이펙트 SVG는 `design/arcade/` 에 준비되어 있습니다 (쓰레기 4종, 위험 2종, 배경 3레이어, 이펙트 3종). 겉모습만 있고 질량(kg)·점수 같은 데이터는 이 마일스톤에서 정합니다.

**완료 기준 (DoD)**

- [x] 조이스틱이 자연스럽게 조작되고 관성이 체감된다 — 포인터 이벤트 기반, 브라우저 자동화로 검증. **실기기 터치 확인은 남음**
- [x] 60fps를 유지한다 — 34개 기준 평균 59.7fps, p95 16.8ms
- [x] 쓰레기에 닿으면 자동으로 흡수되고 줍스가 눈에 띄게 커진다 — 20초 플레이에서 0 → 3.3kg, 반지름 4 → 4.61
- [x] 위험 파편에 부딪혀도 게임이 끊기지 않고 크기/점수만 줄어든다
- [x] 60초 후 자동 종료되며 이번 세션 청소량(kg)이 요약된다
- [x] 성장 판정·점수 계산 로직이 순수 함수로 분리되어 단위 테스트가 있다 — `lib/game/`, 테스트 65건

**선행 조건**: M0

**실측 완료**: SVG 동시 오브젝트 상한 약 200개 (현재 설정 34개, 여유 6배). 상세는 [`decisions.md`](./decisions.md) ADR-002.

**남은 것**: 실기기 터치 조작 확인. 브라우저 자동화의 포인터 이벤트는 실제 손가락의 접촉 면적·이동 곡선과 다르므로 감쇠 계수(`JUPSY_DAMPING_PER_SECOND`)는 실기기에서 재조율할 여지가 있다.

## M2 — 누적 실적 & 프로필 ✅

**목표**: 한 판의 결과가 사라지지 않고 쌓이게 한다. "자긍심"이라는 기획 의도가 처음으로 작동하는 지점.

**범위**

- `lib/storage.ts`: localStorage 읽기/쓰기. **스키마 버전 필드 포함** (추후 마이그레이션 대비)
- 세션 종료 시 누적 청소량(kg)·플레이 횟수 누적
- 프로필 화면 (`app/profile/page.tsx`): 누적 청소량, 체감 비유 환산("자동차 3대 무게"), 담당 궤도 구역 정화율
- 궤도 구역 시각화: 쓰레기 점이 누적량에 비례해 사라지는 SVG
- 배지 시스템: "첫 1kg 청소" 등 명예 기록. **재화·상점 없음**
- SSR hydration 안전 처리 (localStorage는 서버에 없음 → 첫 렌더 불일치 회피)

> `design/ui/orbit-sector.svg` 에 궤도 구역 시각화가 준비되어 있습니다. 쓰레기 점에 `orbit-dot-01`~`36` 개별 id가 붙어 있어 정화율만큼 앞에서부터 지우면 됩니다. 배지는 **빈 프레임만** 있습니다 — Q3(배지 종류와 조건)의 결론이 나야 채울 수 있습니다.

**완료 기준 (DoD)**

- [x] 플레이 → 새로고침 → 프로필에 누적치가 남아 있다 — 60초 실플레이에서 14.67kg 저장 후 유지 확인
- [x] hydration mismatch 경고가 콘솔에 없다 — `useSyncExternalStore`의 `getServerSnapshot`으로 구조적으로 차단 (ADR-011)
- [x] 저장 데이터가 없는 첫 방문자도 화면이 깨지지 않는다 — 0kg / "아직 기록이 없어요" / 배지 0-8
- [x] 배지 획득 조건 계산에 단위 테스트가 있다 — 경계값(0.99kg vs 1kg) 포함
- [x] 저장 스키마에 버전 필드가 있고, 알 수 없는 버전일 때의 동작이 정의되어 있다 — 백업 키로 이동 후 빈 상태 (ADR-011)

**선행 조건**: M1

## M3 — 캐릭터 비주얼 고도화

**목표**: 줍스가 "귀엽다"는 감정을 실제로 일으키게 만든다. 애착이 이 게임의 핵심 동력이므로 미룰 수 없는 단계.

**범위**

- `components/Jupsy.tsx`: 확정된 디자인 언어를 SVG로 구현 — 아이보리색 라운드-코너 케이싱, CRT 스크린풍 바이저, 몸통에서 **분리되어 떠 있는 팔**, 고양이 귀 센서, 등 가시, 수염 와이어(안테나 겸용), 가슴 코어 라이트(앰버 인디케이터)
- 바이저 표정 세트: `normal` / `happy` / `hurt` / `heart` — 바이저를 디스플레이로 취급해 **눈 도형만 교체**
- CSS 애니메이션: 부유(idle bobbing), 흡수 시 통통 튐, 피격 시 흔들림, 코어 라이트 맥동
- `prefers-reduced-motion` 대응

> **SVG 원본은 `design/character/` 에 있습니다.** 이 마일스톤의 일은 새로 그리는 것이 아니라 컴포넌트로 옮기고 애니메이션을 붙이는 것입니다. 눈 슬롯 규격·파트별 `transform-origin`·표정↔이벤트 매핑은 [`design-guide.md`](./design-guide.md) 4·5절에 있습니다.
>
> **디자인 방향 전환(PR #5 검토 반영)**: 협업자가 제안한 4개 테마 디자인 PR 검토 후, 캐릭터를 포함한 비주얼 언어를 **카세트 퓨처리즘**으로 교체했습니다(이전: 월-E 이브 참고 스타일). `jupsy-base.svg`와 표정 8종 중 `focus`·`happy`·`hurt` 3종, 그리고 아케이드 파편 2종(`debris-metal`·`debris-crystal`)·위험요소 1종(`hazard-blade`)·배경 1겹(`starfield`)이 새 방향으로 갱신됐습니다. 나머지 표정 5종(`normal`·`blink`·`curious`·`heart`·`sleepy`), 파편 2종(`debris-archive`·`debris-cable`), 위험요소 1종(`hazard-shard`), 배경 2겹(`earth-limb`·`orbit-band`), 이펙트 3종, UI(궤도 정화율·배지)는 협업자에게 요청한 후속 GitHub 이슈에서 채워질 때까지 이전 스타일로 남아 있습니다 — M3 착수 전 이 이슈가 먼저 해소되어야 완전한 세트로 시작할 수 있습니다.

**완료 기준 (DoD)**

- [ ] 표정 추가가 눈 도형 교체만으로 가능하다 (몸통 구조 수정 불필요)
- [ ] 좋아하는 것을 먹으면 눈이 하트가 되고 통통 튄다
- [ ] 애니메이션이 M1에서 측정한 프레임률을 떨어뜨리지 않는다
- [ ] `prefers-reduced-motion: reduce`에서 애니메이션이 줄어든다

**선행 조건**: M1 (M2와 병렬 진행 가능)

## M4 — 지구 레이어 온보딩

**목표**: 입양부터 발사까지의 서사를 붙인다. 여기까지 오면 게임의 앞뒤가 맞는다.

**범위**

- Day 0~2 유대 형성: 먹이 주기 / 놀아주기 인터랙션
- 진행 상태를 유한 상태 머신으로 모델링 (입양 → 유대 형성 → 발사 준비 → 카운트다운 → 궤도 진입)
- 발사 카운트다운 연출
- 첫날 임팩트를 압축적으로 주는 연출 설계

**완료 기준 (DoD)**

- [ ] 신규 유저가 온보딩을 거쳐 발사까지 도달한다
- [ ] 이미 발사한 유저는 온보딩을 다시 보지 않는다
- [ ] 상태 전이 규칙이 한 곳에 모여 있고 단위 테스트가 있다

**선행 조건**: M2 (저장 구조 필요)

## M5 — 통신 가능 시간 시스템

**목표**: "진짜 위성처럼" 정해진 시간에만 만날 수 있게 한다. 세계관의 핵심 장치.

**범위**

- 궤도 주기 기반 패스 타임 스케줄 — 완전 랜덤이 아니라 **매일 조금씩 밀리는** 방식
- 접속 게이트: 패스 타임이 아니면 아케이드 모드 진입 불가, 다음 패스까지 카운트다운 표시
- 알림 (Notification API / PWA)
- 세션 길이를 프로토타입 60초 → 실제 2~5분으로 조정할지 결정

**완료 기준 (DoD)**

- [ ] 오늘의 패스 타임이 표시되고, 매일 일정하게 밀린다
- [ ] 패스 타임 외에는 아케이드 진입이 막히고 이유가 안내된다
- [ ] 기기 시간대가 바뀌어도 스케줄이 깨지지 않는다

**선행 조건**: M4

**미결정**: 하루 몇 회, 각 창의 길이, 밀리는 폭. M5 착수 시 결정 필요.

## M6 — 성격 유형 분화

**목표**: 4가지 유형이 실제 플레이에 영향을 주게 한다.

**범위**

- 메탈형 / 크리스탈형 / 아카이브형 / 케이블형 — 판별 유니온 타입으로 정의
- 선호 쓰레기 흡수 시 보너스
- 유형별 외형 변주 (M3의 SVG 구조 위에 레이어 추가)
- 유형 결정 방식: 먹은 쓰레기 종류의 누적 분포로 자동 분화

**완료 기준 (DoD)**

- [ ] 유형 추가가 데이터 정의 추가만으로 가능하다 (분기문 확산 없음)
- [ ] 플레이 패턴에 따라 유형이 실제로 갈린다

**선행 조건**: M2, M3

**미결정**: 유형이 고정인지 재분화 가능한지. M6 착수 시 결정 필요.

## M7 — 서버 저장 & 바이럴

**목표**: 기기를 넘어 기록이 이어지고, 사람과 사람 사이로 퍼지게 한다.

**범위**

- 계정 기반 저장으로 마이그레이션 (localStorage → 서버)
- 분양권/티켓 공유 메커닉
- 발사 이벤트 공유

**완료 기준 (DoD)**

- [ ] 기존 localStorage 데이터가 계정으로 이관된다

### Q2 결론 — 수치는 그대로, 환산을 사다리로

M2에서 프로필 화면을 만들며 결론이 났습니다. 한 판에 약 10~15kg인데, "자동차 3대 무게"(약 3,600kg)는 **300판 가까이** 걸립니다. 비유가 도달 불가능한 곳에 있었습니다.

**밸런스 수치는 건드리지 않았습니다.** 실제 우주 파편이 무겁지 않다는 세계관 진정성을 지키는 쪽이 맞고, 수확량을 억지로 올리면 "작은 실천"이라는 기획 의도와도 어긋납니다.

대신 환산 비유를 **사다리**로 만들었습니다 — 캔 음료 → 노트북 → 자전거 → 세탁기 → 소형차 → 버스. 누적량에 맞는 칸을 자동으로 골라 항상 1 이상의 숫자가 나오고, 다음 칸이 늘 보입니다. 구현은 `lib/game/records.ts`의 `massComparison`.
