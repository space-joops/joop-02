# 기술 결정 기록 (ADR)

이 프로젝트에서 내린 기술 선택과 **그 근거**를 남깁니다. "무엇을 골랐는가"보다 "왜 골랐고 무엇을 포기했는가"가 중요합니다. 나중에 결정을 뒤집어야 할 때, 당시의 전제가 아직 유효한지 판단하는 근거가 됩니다.

## 작성 규칙

- 새 기술 선택을 할 때마다 번호를 이어 추가합니다
- 결정을 뒤집을 때는 기존 항목을 지우지 말고 상태를 `대체됨 (→ ADR-0NN)`으로 바꿉니다
- 상태: `채택` / `잠정` / `대체됨` / `폐기`

### 템플릿

```markdown
## ADR-0NN: 제목

- **상태**: 채택
- **날짜**: YYYY-MM-DD

**맥락** — 어떤 상황에서 이 결정이 필요했는가

**결정** — 무엇으로 정했는가

**대안** — 검토했지만 선택하지 않은 것들

**근거** — 왜 이걸 골랐는가

**결과** — 이 선택이 만들어내는 제약과 앞으로 감시해야 할 지점
```

## ADR-001: Next.js 14 (App Router) + TypeScript

- **상태**: 대체됨 (→ [ADR-008](#adr-008-nextjs-16--react-19로-상향-adr-001-대체))
- **날짜**: 2026-07-25 (프로젝트 초기 결정을 소급 기록)

> 프레임워크 선택(Next.js App Router + TypeScript)과 그 근거는 그대로 유효합니다. **버전만 14 → 16으로 대체**되었습니다. 경위는 ADR-008 참고.

**맥락** — 모바일 세로 화면 고정 웹 게임. 별도 앱 설치 없이 링크로 퍼져야 한다(바이럴 요구사항).

**결정** — Next.js 14 App Router + TypeScript, Vercel 배포.

**대안** — Vite + React SPA (더 가볍고 빌드가 빠름), 네이티브 앱 (성능·알림 유리).

**근거** — 링크 하나로 전달되는 접근성이 바이럴 컨셉의 전제다. Vercel 무설정 배포와 App Router의 파일 기반 라우팅이 프로토타입 속도에 유리하다. TypeScript는 게임 상태(줍스 상태, 쓰레기 종류, 성격 유형)가 곧 복잡해질 것이므로 처음부터 도입한다.

**결과** — 게임 화면은 대부분 클라이언트 컴포넌트가 된다. RSC의 이점을 크게 못 누리는 대신, 서버 저장(M7)을 붙일 때 Server Actions을 쓸 수 있다. **감시 지점**: `'use client'` 경계가 필요 이상으로 위로 올라가지 않도록 관리.

## ADR-002: SVG + CSS 렌더링 (Canvas 2D 배제)

- **상태**: 채택
- **날짜**: 2026-07-25 (소급 기록)

**맥락** — 줍스의 표정 변화가 게임의 정서적 핵심이다. 동시에 수십 개의 쓰레기 오브젝트가 움직이는 아케이드 모드도 필요하다.

**결정** — 모든 그래픽과 애니메이션을 SVG + CSS로 구현한다. Canvas 2D를 쓰지 않는다.

**대안** — Canvas 2D (오브젝트가 많을 때 성능 유리), WebGL/PixiJS (가장 빠르지만 과함).

**근거** — 표정 시스템이 "바이저를 디스플레이로 취급해 눈 도형만 교체"하는 구조인데, 이는 선언적 DOM에서 압도적으로 다루기 쉽다. Canvas였다면 매 프레임 다시 그려야 한다. DevTools로 요소를 직접 검사할 수 있어 디버깅도 빠르다. 접근성 처리도 SVG 쪽이 낫다.

**결과** — **동시 오브젝트 수가 성능 상한이 된다.** 개별 SVG 요소의 transform을 매 프레임 갱신하면 레이아웃·페인트 비용이 오브젝트 수에 비례한다.

**⚠️ 감시 지점** — M1에서 오브젝트 수를 늘려가며 60fps가 깨지는 지점을 실측하고 이 항목에 기록한다. 상한이 게임 디자인(동시 스폰 수)을 감당하지 못하면 이 ADR을 재검토한다. 완화책: `transform`만 사용해 컴포지팅 레이어에서 처리, 화면 밖 오브젝트 언마운트.

### 실측 결과 (M1, 2026-07-25)

측정 환경: headless Chromium, 393×852 @2x, `MAX_DEBRIS`를 바꿔가며 각 6초간 프레임 간격 샘플링.

| 동시 오브젝트 | 평균 fps | p95 프레임 시간 |
| --- | --- | --- |
| 34 (현재 설정) | 60.0 | 16.8ms |
| 80 | 59.7 | 16.8ms |
| 149 | 58.0 | 16.8ms |
| 200 | 56.2 | 16.8ms |
| **250** | **49.7** | **33.4ms** |
| 300 | 32.4 | 66.6ms |
| 500 | 20.4 | 100.1ms |

**결론: 실사용 상한은 약 200개.** 200까지는 p95가 16.8ms(=한 프레임)에 머물러 프레임 드랍이 없다. 250에서 p95가 33.4ms로 뛴다 — 두 프레임에 한 번씩 놓치기 시작하는 지점이다. 그 위로는 급격히 무너진다.

**현재 게임 설정은 34개다.** 측정된 상한 대비 약 6배의 여유가 있다. SVG 선택이 이 게임의 디자인을 제약하지 않는다는 뜻이므로 **ADR-002는 유지한다.**

**⚠️ 이 수치를 그대로 믿으면 안 되는 이유** — 서버 CPU의 headless Chromium에서 잰 값이다. 실제 중급 휴대폰은 이보다 상당히 낮다. 여유가 6배라 34개 설정은 안전하다고 보지만, **동시 오브젝트를 100개 이상으로 늘리려면 실기기에서 다시 재야 한다.**

성능에 기여한 구현 선택 (바꾸면 이 수치도 무효가 된다)

- 모든 오브젝트를 반지름 1로 그리고 `transform`의 scale로 크기를 준다 → 매 프레임 갱신이 속성 한 번 쓰기로 끝난다
- 좌표를 React state가 아니라 DOM 직접 조작으로 갱신한다 → 리렌더가 초당 60회에서 두어 번으로 줄어든다
- `will-change: transform`으로 컴포지팅 레이어에 올려 레이아웃·페인트를 건너뛴다

## ADR-003: CSS Modules + CSS 변수 (Tailwind 배제)

- **상태**: 채택
- **날짜**: 2026-07-25

**맥락** — 스타일링 방식이 정해져 있지 않았다. 이 프로젝트는 일반적인 UI 화면(홈·프로필)과 게임 애니메이션(줍스 표정·부유·피격)이 섞여 있다.

**결정** — CSS Modules를 쓰고, 색상·간격·타이포·z-index를 `:root`의 CSS 변수로 정의한다.

**대안** — Tailwind CSS (UI 화면을 빠르게 짤 수 있고 실무 채택률이 높음), Tailwind + CSS Modules 혼용.

**근거** — 이 게임 비중의 상당수가 키프레임 애니메이션인데, Tailwind는 결국 별도 CSS로 빠진다. 그러면 규칙이 두 벌이 되고 어디에 무엇을 쓸지 계속 판단해야 한다. CSS 변수 기반 디자인 토큰은 런타임에 값을 바꿀 수 있어 줍스의 기분에 따라 색을 바꾸는 연출에도 그대로 쓰인다. 의존성도 추가되지 않는다.

**결과** — UI 화면 작성 속도는 Tailwind보다 느리다. 대신 토큰 체계를 직접 설계하게 되므로 디자인 시스템 감각이 남는다. **규칙**: 컴포넌트에 색상·간격 리터럴을 직접 쓰지 않고 반드시 변수를 거친다.

## ADR-004: 게임 루프는 requestAnimationFrame + delta time

- **상태**: 채택
- **날짜**: 2026-07-25

**맥락** — 조이스틱 관성 이동과 충돌 판정을 매 프레임 계산해야 한다.

**결정** — `requestAnimationFrame` 루프를 쓰고, 이전 프레임과의 시간 차(delta)로 이동량을 정규화한다. 게임 상태는 `useRef`에 두고, 화면에 반영할 값만 프레임 단위로 렌더에 반영한다.

**대안** — `setInterval` (프레임과 어긋나 끊김 발생), delta 없이 프레임당 고정 이동량 (기기 주사율에 따라 속도가 달라짐 — 120Hz 기기에서 2배 빨라짐).

**근거** — rAF는 브라우저 렌더 주기와 동기화되고 백그라운드 탭에서 자동으로 멈춘다(배터리). delta time 정규화는 주사율이 제각각인 모바일 환경에서 필수다.

**결과** — 게임 상태를 `useState`에 두면 매 프레임 리렌더가 발생해 성능이 무너진다. **규칙**: 좌표·속도 같은 고빈도 값은 `useRef` + DOM 직접 조작, 점수·타이머 같은 저빈도 값만 `useState`.

## ADR-005: localStorage 우선, 서버 저장은 M7로 유예

- **상태**: 잠정
- **날짜**: 2026-07-25 (소급 기록)

**맥락** — 누적 청소량이 이 게임의 보상 그 자체이므로 반드시 남아야 한다. 하지만 초기에 백엔드를 세우면 프로토타입 속도가 크게 느려진다.

**결정** — 브라우저 `localStorage`에 저장한다. 서버·계정 저장은 M7로 미룬다.

**대안** — 처음부터 Supabase 등 BaaS 도입.

**근거** — M1~M3에서 검증할 것은 "재미있는가"이지 "데이터가 안전한가"가 아니다. 인증 UI가 첫 진입 장벽이 되면 바이럴 컨셉과도 충돌한다.

**결과** — **기기를 바꾸면 실적이 사라진다.** 이 게임에서 누적 실적이 곧 자긍심이므로 장기적으로는 치명적인 제약이다.

**완화** — M2부터 저장 데이터에 **스키마 버전 필드**를 넣어 M7 마이그레이션에 대비한다. 저장 접근은 `lib/storage.ts` 한 곳으로만 하고, 나머지 코드가 localStorage를 직접 만지지 않게 한다.

## ADR-006: 품질 도구 — ESLint + Prettier + Vitest + GitHub Actions

- **상태**: 채택
- **날짜**: 2026-07-25

**맥락** — 1인 프로젝트지만 학습 목표(1티어 프론트엔드 역량)가 명시되어 있고, 게임 로직에는 눈으로 검증하기 어려운 계산(성장 판정, 점수, 배지 조건)이 있다.

**결정** — ESLint + Prettier로 정적 검사, Vitest로 단위 테스트, GitHub Actions에서 `lint → test → build`를 검증한다. Playwright E2E는 도입하지 않는다.

**대안** — 린트/포맷만 (빠르지만 로직 회귀를 못 잡음), Playwright E2E까지 (초기 설정 비용이 큼).

**근거** — 게임 로직 테스트의 관건은 **순수 함수로 분리하는 것**이고, 테스트를 쓰기로 하면 자연히 그 분리가 강제된다. 이 설계 압력이 테스트 자체보다 가치가 크다. E2E는 조이스틱 드래그 같은 연속 포인터 입력 검증 비용이 커서 지금은 투자 대비 효과가 낮다.

**결과** — 테스트 가능한 형태로 로직을 짜야 한다. `lib/`에 순수 함수를, 컴포넌트에 렌더링과 입력 처리를 두는 경계가 생긴다. **감시 지점**: 아케이드 플로우 전체를 검증할 수단이 없으므로 M1 완료 시 E2E 도입을 재검토한다.

## ADR-007: 보상에서 재화·상점 배제

- **상태**: 채택
- **날짜**: 2026-07-25 (소급 기록)

**맥락** — 청소 실적을 무엇으로 보상할지. 게임의 관성적 선택은 재화 지급 → 상점 구매다.

**결정** — 재화와 상점을 만들지 않는다. 누적 청소량(kg), 궤도 정화율, 명예 배지만 둔다.

**대안** — 재화 + 꾸미기 상점 (리텐션에 유리한 검증된 패턴).

**근거** — 이 게임의 기획 의도는 줍깅처럼 **작은 실천이 자긍심이 되는 경험**이다. 청소가 재화 획득 수단이 되는 순간 동기가 "환경을 치웠다"에서 "돈을 벌었다"로 바뀌고, 세계관의 진정성이 깨진다. 자랑거리가 되어야 퍼지는데, 자랑할 것은 게임 화폐가 아니라 **실제 성과 기록**이다.

**결과** — 상점이라는 흔한 리텐션 장치를 포기했다. 대신 배지·정화율 시각화·유형 분화가 그 역할을 대신해야 하므로, 이들의 완성도가 곧 게임의 수명이다.

**감시 지점** — 누적 실적이 다음 세대 줍스 분양 자격과 연결되는 아이디어(미확정)는 이 원칙에 부합하는지 검토 후 결정한다.

## ADR-008: Next.js 16 + React 19로 상향 (ADR-001 대체)

- **상태**: 채택
- **날짜**: 2026-07-25

**맥락** — M0 스캐폴딩에서 ADR-001대로 Next.js 14.2.35(14.x 마지막 버전)를 설치한 뒤 `npm audit`을 돌렸더니 `next`에 미패치 권고가 **21건**(high 7건) 나왔다. 개별 권고의 수정 버전을 확인해 보니 **전부 15.5 이상에서만 수정**되었고, 14.x 안에는 어떤 조합으로도 안전한 버전이 없었다. Next 14는 사실상 EOL이다.

**결정** — Next.js **16.2.11** + React **19.2.4**로 상향한다. 프레임워크 선택(Next.js App Router + TypeScript)과 ADR-001의 근거는 그대로 유지하고, 버전만 바꾼다.

**대안**

- Next 14 유지 — CLAUDE.md 기록과 일치하지만 보안 업데이트를 받지 못한다
- Next 15.5 최신 — 권고를 해소하는 최소 상향. 변화폭이 작지만 머지않아 다시 올려야 한다

**근거** — 이 게임의 실제 노출도는 낮다. 권고 상당수가 self-hosted DoS, rewrites SSRF, Image Optimizer 관련인데 Vercel 배포에 거의 클라이언트 전용 게임이라 해당 기능을 쓰지 않는다. 그럼에도 **EOL 프레임워크 위에서 새 프로젝트를 시작할 이유가 없다.** CI에 audit 경고가 상시로 남는 것도 "CI를 신뢰의 근거로 쓴다"는 이 프로젝트의 품질 기준(ADR-006)과 어긋난다.

**결과 — Next 16은 14와 설정 규약이 다르다.** `create-next-app`으로 정본 설정을 확인해 반영했다.

| 항목 | Next 14 | Next 16 |
| --- | --- | --- |
| 린트 | `next lint` | `next lint` 제거 → `eslint` 직접 호출 |
| ESLint 설정 | `.eslintrc.json` | `eslint.config.mjs` (flat config) |
| next 설정 | `next.config.mjs` | `next.config.ts` |
| tsconfig `jsx` | `preserve` | `react-jsx` |
| React | 18 | 19 |

**남은 취약점과 그 판단**

`next` 자체에는 직접 권고가 없다. 다만 번들된 의존성을 통해 전이로 잡히는 것이 있어 다음과 같이 처리했다.

- **postcss / sharp** — `overrides`로 패치 버전(postcss ^8.5.23, sharp ^0.35.3)을 고정해 해소했다. npm이 제안한 "수정"은 next@9.3.3 다운그레이드였는데, 이는 resolver가 최소 버전을 찾은 결과일 뿐 실제 해법이 아니다.
- **eslint 의존성 체인 (9건, high)** — 근원은 `brace-expansion`의 DoS다. 수정에 eslint 10이 필요한데 `eslint-config-next@16`이 eslint `^9`를 고정한다. `minimatch@3` / `brace-expansion@1`을 메이저 4개를 건너뛰어 override하면 lint가 조용히 깨질 위험이 실익보다 크다. **dev 전용이고 공격 벡터가 "우리가 직접 작성한 glob 패턴"이라 실제 노출이 없어** 상향하지 않았다.

**감시 지점** — `eslint-config-next`가 eslint 10을 지원하면 남은 9건을 해소한다. 그 전까지 `npm audit`의 high 9건은 **알려진 상태**이므로, 새 항목이 추가되었는지만 확인하면 된다.
