### 배운 점

**스스로 ADR-004를 어긴 걸 lint가 아니라 코드를 다시 읽다가 발견했다.** 타이머를 `setRemaining(left)`로 매 프레임 호출하고 있었다. `left`는 float이라 매번 값이 달라지고, 결국 초당 60회 리렌더가 난다 — "고빈도 값은 ref, 저빈도만 state"라고 ADR에 써놓고 정확히 그걸 어긴 것이다. 화면에 보이는 건 초 단위이므로 `Math.ceil`이 바뀔 때만 반영하도록 고쳤다. **규칙을 문서에 적는 것과 코드에서 지키는 것은 별개다.**

**React 19의 순수성 lint 규칙이 설계를 개선시켰다.** 처음엔 파편 목록을 ref 하나로 두고 렌더에서 `debrisRef.current.map(...)`으로 그렸는데 "Cannot access refs during render"로 막혔다. 우회하지 않고 ref(루프용)와 state(렌더용) 두 벌로 나눴더니, "매 프레임 바뀌는 위치"와 "가끔 바뀌는 목록 구성"이라는 두 성격이 코드에서 분리됐다. 규칙이 없었다면 한 덩어리로 뒀을 것이다. `useRef(createSpawner(Date.now()))`도 같은 이유로 막혀서 rAF 콜백 안 지연 생성으로 바꿨다.

**delta time 정규화는 이동뿐 아니라 감쇠에도 필요하다.** 프레임마다 `vel *= 0.9`를 곱하면 120Hz 기기가 60Hz의 두 배로 감쇠해 조작감이 달라진다. "1초에 남는 비율"을 정의하고 `ratio ** dt`로 환산해야 주사율과 무관해진다. 이 부분은 테스트로 못 박아 뒀다(60Hz와 120Hz에서 1초 뒤 위치 비교).

**dt 상한이 없으면 충돌 판정이 통째로 건너뛰어진다.** 탭 전환 후 복귀하면 dt가 수 초로 튀는데, 그대로 적분하면 줍스가 화면을 가로질러 순간이동한다. 그 사이에 있던 파편은 판정 자체가 일어나지 않는다. 1/20초 상한을 걸어 느려질지언정 상태가 깨지지 않게 했다.

**자기 검증 질문 중 답하지 못한 것** ([`growth-roadmap.md`](./growth-roadmap.md) M1)

- "조이스틱을 조작하는 동안 컴포넌트가 몇 번 리렌더되는가" — 구조상 손가락 움직임으로는 리렌더가 나지 않게 짰지만(입력을 ref에 담음), **실제 횟수를 측정하지는 않았다.** React DevTools Profiler로 세어봐야 한다. 프레임률이 좋다고 리렌더가 없다는 증거는 아니다.
- "원인이 스크립트인지 레이아웃인지 페인트인지 프로파일러로 구분할 수 있는가" — 이번엔 프레임 간격만 쟀지 Performance 패널로 단계를 쪼개보지 않았다. 60fps가 나와서 파고들 필요가 없었지만, **파고들 필요가 없었던 것과 할 줄 아는 것은 다르다.**

### 한 일

**계획을 벗어난 결정이 하나 있었다.** ADR-001이 Next.js 14를 명시해서 14.2.35(14.x 마지막)를 설치했는데, `npm audit`에서 `next` 미패치 권고가 21건(high 7건) 나왔다. 개별 권고의 수정 버전을 확인해 보니 **전부 15.5 이상에서만 수정**되어 14.x 안에는 안전한 조합이 없었다. 사용자 승인을 받아 Next 16 + React 19로 상향하고 ADR-008로 기록했다.

### 검증

- CI가 실행할 6단계를 로컬에서 같은 순서로 재현 — `npm ci`부터 전부 통과
- Playwright로 실제 렌더 확인 — iPhone 14 Pro 세로(393×852)에서 레이아웃 정상, 좁은 가로(852×393)에서 회전 안내로 정상 대체
- 빌드 결과 라우트가 `/`와 `/_not-found`뿐임을 확인 — `app/` 안의 테스트 파일이 라우트로 잡히지 않는다
- `npm audit` — high 9건 잔존 (전부 eslint 의존성 체인, 판단 근거는 ADR-008)

### 배운 점

- **버전을 문서에 박아두면 그 문서가 낡는 속도만큼 프로젝트도 낡는다.** ADR-001은 "Next.js 14"라고 버전까지 결정으로 적었는데, 정작 중요한 결정은 "Next.js App Router + TypeScript"였고 마이너 버전은 부수적이었다. ADR-008에서 이 둘을 분리해 "프레임워크 선택은 유효, 버전만 대체"로 적었다. 앞으로 ADR을 쓸 때 **무엇이 진짜 결정이고 무엇이 그 시점의 구현 세부인지** 구분해야 한다.
- **`npm audit`의 "fix available"을 그대로 믿으면 안 된다.** postcss/sharp 권고에 npm이 제안한 수정은 `next@9.3.3` 다운그레이드였다. resolver가 조건을 만족하는 최소 버전을 찾은 것일 뿐 해법이 아니었다. 실제 해법은 `overrides`로 전이 의존성만 패치 버전에 고정하는 것이었다.
- **취약점은 "고친다/방치한다"의 이분법이 아니다.** 남은 eslint 체인 9건은 dev 전용이고 공격 벡터가 우리가 직접 쓴 glob 패턴이라 실제 노출이 없다. 메이저를 4개 건너뛰어 override하면 lint가 조용히 깨질 위험이 실익보다 컸다. **판단 근거를 ADR에 남겨두면 다음에 같은 경고를 봤을 때 재조사할 필요가 없다.**
- Prettier가 한글 표를 망가뜨린다는 것을 커밋한 문서가 통째로 재정렬된 뒤에야 알았다. 문자 폭을 코드포인트로 세기 때문인데, 한글은 전각이라 표시 폭과 어긋난다. `*.md`를 포맷 대상에서 제외했다.

**자기 검증 질문 중 답하지 못한 것** ([`growth-roadmap.md`](./growth-roadmap.md) M0)

- "`'use client'`를 어느 지점에 붙이는 게 최선인가" — 아직 클라이언트 컴포넌트가 하나도 없어서 판단할 기회가 없었다. **M1에서 조이스틱을 만들 때가 첫 시험대다.**

### 배운 점

- **문서가 코드보다 앞서 나가면 문서가 아니라 오해가 된다.** 기존 CLAUDE.md는 "이렇게 만들 것"이라는 계획과 "이렇게 만들어져 있다"는 현황을 같은 문장 톤으로 섞어 썼고, 그 결과 다음에 읽는 사람이 없는 파일을 읽으려 하게 만들었다. 이번 정비에서 **계획과 현황을 문서 자체로 분리**했다 — 현황은 CLAUDE.md의 `현재 상태` 섹션 한 곳에만, 계획은 `docs/roadmap.md`에.
- 결정만 적고 근거를 안 적으면 나중에 뒤집을지 판단할 수 없다. ADR에 `근거`뿐 아니라 **`감시 지점`**(전제가 깨졌을 때 재검토할 조건)을 넣었다. 예: ADR-002는 SVG 렌더링의 오브젝트 수 상한이 게임 디자인을 감당 못 하면 재검토하도록, M1 실측값을 채울 빈칸을 남겨뒀다.
- 미결정 사항을 "미확정"이라고만 적어두면 영원히 미확정으로 남는다. 각 질문에 **결론이 나야 하는 마일스톤**을 붙였다.
