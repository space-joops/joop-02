# 문서 인덱스

줍스(Jupsy) 프로젝트의 문서 지도입니다. **처음 이 프로젝트를 여는 사람은 여기서 시작하세요.**

## 읽는 순서

1. [`../CLAUDE.md`](../CLAUDE.md) — 이 게임이 무엇이고 무엇이 정해져 있는가
2. [`roadmap.md`](./roadmap.md) — 지금 어디까지 왔고 다음에 무엇을 만드는가
3. [`worklog.md`](./worklog.md) — 최근에 무슨 일이 있었는가

## 문서별 역할

| 문서 | 역할 | 언제 갱신하는가 |
| --- | --- | --- |
| [`../CLAUDE.md`](../CLAUDE.md) | **프로젝트 헌법.** 컨셉·세계관·확정된 게임 규칙·기술 결정 요약·현재 상태 | 기획이 바뀌거나, 마일스톤을 완료해 `현재 상태`가 달라졌을 때 |
| [`roadmap.md`](./roadmap.md) | **무엇을 어떤 순서로.** M0~M7 마일스톤의 목표·범위·완료 기준·미결정 질문 | 마일스톤 착수/완료 시 `현재 위치` 표를 갱신. 질문에 결론이 나면 목록에서 제거 |
| [`decisions.md`](./decisions.md) | **왜 그렇게 정했나.** 기술 선택의 맥락·대안·근거·감시 지점 | 새 기술 선택을 할 때마다 ADR 추가. 결정을 뒤집을 때는 지우지 말고 `대체됨`으로 표시 |
| [`worklog.md`](./worklog.md) | **무슨 일이 있었나.** 날짜별 작업·검증·배운 점·측정 수치 | **작업이 끝날 때마다.** 특히 성능 측정 수치는 그때 적지 않으면 재현이 어렵다 |

## 작업을 마칠 때의 규칙

1. **[`worklog.md`](./worklog.md)에 기록한다** — 예외 없이
2. 새로운 기술 선택을 했다면 **[`decisions.md`](./decisions.md)에 ADR을 추가한다**
3. 마일스톤을 완료했다면 **[`roadmap.md`](./roadmap.md)의 `현재 위치` 표**와 **[`growth-roadmap.md`](./growth-roadmap.md)의 축별 진척 표**를 갱신한다
4. 실제 구현 상태가 달라졌다면 **[`../CLAUDE.md`](../CLAUDE.md)의 `현재 상태` 섹션**을 갱신한다

## 문서를 쓸 때의 원칙

이 프로젝트는 한 번 문서 때문에 손해를 본 적이 있습니다. 초기 CLAUDE.md가 **존재하지 않는 6개 파일을 "구현 완료"로 서술**하고 있었고, 그 위에서 작업을 이어가려던 시도가 모두 헛돌았습니다. (경위는 [`worklog.md`](./worklog.md) 2026-07-25 항목 참고.)

그래서 다음 두 가지를 지킵니다.

- **계획과 현황을 같은 톤으로 쓰지 않는다.** 현황은 `CLAUDE.md`의 `현재 상태` 한 곳에만 적고, 나머지는 전부 계획으로 명시한다
- **확인하지 않은 것을 단정형으로 쓰지 않는다.** 파일 구조나 구현 상태를 적을 때는 실제로 존재하는지 확인한 뒤에 쓴다
