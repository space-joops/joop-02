# 1티어 프론트엔드 성장 로드맵

이 문서는 **줍스 프로젝트를 만들면서 프론트엔드 역량을 어디까지 끌어올릴 것인가**를 정의합니다. 별도의 학습 계획이 아니라, [`roadmap.md`](./roadmap.md)의 각 마일스톤에 학습 주제를 붙인 커리큘럼입니다. 마일스톤을 완료하면 해당 역량이 **산출물로 증명되도록** 설계했습니다.

## 왜 이렇게 짰는가

강의를 듣고 잊는 대신, 실제로 부딪혀야만 배워지는 주제를 골랐습니다. 이 프로젝트는 그런 주제를 유난히 많이 품고 있습니다.

- 60fps를 유지해야 하는 실시간 루프 → **렌더링 성능과 리렌더 통제**를 이론이 아니라 프로파일러로 배운다
- 터치 조이스틱 → **포인터 이벤트와 입력 처리**를 라이브러리 없이 다룬다
- 표정·성격 유형 → **타입 설계와 데이터 주도 설계**의 효과가 즉시 드러난다
- localStorage → 서버 마이그레이션 → **상태의 소유권과 스키마 진화**를 실제로 겪는다

## 역량 맵

1티어 프론트엔드 개발자를 6개 축으로 정의합니다. 각 축에서 지금 어디에 있고 어디로 갈지 확인하세요.

### ① 렌더링 / 성능

| 수준 | 상태 |
| --- | --- |
| 주니어 | 화면이 잘 나오면 완료로 본다. 느려지면 원인을 추측한다 |
| 미들 | `memo`·`useCallback`을 알고 쓴다. 하지만 어디에 써야 효과가 있는지는 감으로 판단한다 |
| **1티어** | **브라우저 렌더 파이프라인(스타일→레이아웃→페인트→컴포지팅)을 알고, 프로파일러로 병목을 특정한 뒤 근거를 대며 고친다. 리렌더가 언제 발생하는지 예측할 수 있다** |

→ **M1에서 결판나는 축.** 60fps 목표가 있으므로 추측이 통하지 않습니다.

### ② 상태 설계

| 수준 | 상태 |
| --- | --- |
| 주니어 | 전부 `useState`에 넣는다 |
| 미들 | 상태를 끌어올리고 내리는 판단을 한다. 전역 상태 라이브러리를 쓴다 |
| **1티어** | **상태의 성격(고빈도/저빈도, 서버/클라이언트, 파생/원본)을 구분해 저장 위치를 정한다. 파생 상태를 중복 저장하지 않는다** |

→ **M1(ref vs state), M2(영속 상태), M7(서버 상태)에 걸쳐 다룹니다.**

### ③ 인터랙션 / 입력

| 수준 | 상태 |
| --- | --- |
| 주니어 | `onClick`을 쓴다 |
| 미들 | 터치·마우스 차이를 알고 이벤트를 분기한다 |
| **1티어** | **포인터 이벤트로 통합 처리하고, 캡처·기본동작·패시브 리스너를 이해한다. 관성·감쇠 같은 물리적 감각을 수치로 조율할 수 있다** |

→ **M1의 조이스틱이 이 축 전체입니다.**

### ④ 타입 / 아키텍처

| 수준 | 상태 |
| --- | --- |
| 주니어 | `any`를 쓰거나 타입을 나중에 붙인다 |
| 미들 | 인터페이스를 정의하고 제네릭을 쓴다 |
| **1티어** | **판별 유니온으로 불가능한 상태를 타입 수준에서 표현 불가능하게 만든다. 분기문 대신 데이터로 확장한다** |

→ **M4(상태 머신), M6(성격 유형)에서 다룹니다.**

### ⑤ 품질 (테스트 / CI)

| 수준 | 상태 |
| --- | --- |
| 주니어 | 손으로 눌러보고 확인한다 |
| 미들 | 테스트를 쓸 줄 안다. 다만 테스트하기 위해 억지로 짜맞춘다 |
| **1티어** | **테스트하기 쉬운 구조가 곧 좋은 구조임을 알고, 순수 함수 경계를 먼저 설계한다. CI를 신뢰의 근거로 쓴다** |

→ **M0에서 파이프라인을 깔고, 모든 마일스톤에서 유지합니다.**

### ⑥ 접근성 / UX 디테일

| 수준 | 상태 |
| --- | --- |
| 주니어 | 고려하지 않는다 |
| 미들 | `alt`와 시맨틱 태그를 챙긴다 |
| **1티어** | **`prefers-reduced-motion`, safe-area, 포커스 관리, 터치 타겟 크기 같은 실제 기기 조건을 기본값으로 챙긴다** |

→ **M0(safe-area), M3(reduced-motion)에서 다룹니다.**

### M1 — 아케이드 모드 코어 ⭐ 가장 중요한 구간

**핵심 축**: ① 렌더링/성능, ② 상태 설계, ③ 인터랙션

| 주제 | 이 프로젝트에서 왜 필요한가 |
| --- | --- |
| `requestAnimationFrame` 게임 루프 | `setInterval`과 무엇이 다른지, 왜 프레임 동기화가 필요한지를 몸으로 안다 |
| delta time 정규화 | 60Hz와 120Hz 기기에서 줍스 속도가 같아야 한다. 안 하면 최신 폰에서 2배 빨라진다 |
| **`useState` vs `useRef`** | 좌표를 `useState`에 두면 초당 60회 리렌더가 난다. 이 축의 핵심 |
| React 리렌더 규칙 | 무엇이 리렌더를 유발하고, `memo`가 언제 무의미한지 |
| 브라우저 렌더 파이프라인 | `transform`은 컴포지팅만, `top/left`는 레이아웃부터. 왜 60fps가 갈리는지 |
| DevTools Performance 프로파일링 | 추측하지 않고 측정한다. ADR-002의 오브젝트 상한을 여기서 실측 |
| 포인터 이벤트 | `pointerdown/move/up`으로 터치·마우스 통합. `setPointerCapture`로 손가락이 조이스틱을 벗어나도 추적 |
| 벡터 연산과 관성 | 정규화, 가속도, 감쇠 계수. 관성의 "느낌"은 수치 조율의 결과 |
| 충돌 판정 | 원-원 거리 비교. `Math.sqrt` 생략(제곱 비교) 같은 최적화 |
| 순수 함수 분리 | 성장 판정·점수 계산을 컴포넌트 밖으로 빼야 테스트가 된다 |

**자기 검증 질문**
- 조이스틱을 조작하는 동안 React 컴포넌트가 몇 번 리렌더되는가? 그 숫자를 의도한 값으로 만들었는가?
- 프레임이 떨어질 때, 원인이 스크립트인지 레이아웃인지 페인트인지 **프로파일러로** 구분할 수 있는가?
- `transform: translate()`와 `left/top`의 성능 차이를 렌더 파이프라인 단계로 설명할 수 있는가?
- 120Hz 기기에서 게임 속도가 같다는 것을 어떻게 확인했는가?

**참고 키워드**: `requestAnimationFrame`, `delta time`, `Pointer Events API`, `setPointerCapture`, `compositing layer`, `will-change`, `layout thrashing`, `passive event listener`

**⚠️ 이 마일스톤에서 배운 것을 반드시 [`worklog.md`](./worklog.md)에 남기세요.** 성능 측정 수치는 시간이 지나면 재현이 어렵습니다.

### M2 — 누적 실적 & 프로필

**핵심 축**: ② 상태 설계, ⑤ 품질

| 주제 | 이 프로젝트에서 왜 필요한가 |
| --- | --- |
| 영속화와 스키마 버저닝 | 저장 형식은 반드시 바뀐다. 버전 필드 없이 시작하면 M7에서 기존 유저 데이터를 버려야 한다 |
| **SSR hydration mismatch** | localStorage는 서버에 없다. 서버 렌더 결과와 클라이언트 첫 렌더가 달라지는 전형적 함정 |
| 파생 상태 vs 원본 상태 | 정화율·배지는 누적 kg에서 계산되는 파생값. 따로 저장하면 불일치가 생긴다 |
| 순수 함수 테스트 설계 | 배지 조건·환산 로직을 경계값 중심으로 검증 |
| 방어적 파싱 | 사용자가 localStorage를 손댈 수 있다. 손상된 데이터로 앱이 죽지 않아야 한다 |

**자기 검증 질문**
- hydration mismatch가 왜 생기는지, 해결책 세 가지(`useEffect` 후 렌더 / `suppressHydrationWarning` / 동적 import `ssr:false`)의 트레이드오프를 설명할 수 있는가?
- 저장된 JSON이 손상되었을 때 앱은 어떻게 동작하는가? 그 동작을 의도했는가?
- 파생값 중 실수로 저장하고 있는 것은 없는가?

**참고 키워드**: `hydration mismatch`, `schema migration`, `derived state`, `JSON.parse` 방어, `Vitest` `describe/it`, 경계값 테스트

### M3 — 캐릭터 비주얼 고도화

**핵심 축**: ① 렌더링/성능, ⑥ 접근성

| 주제 | 이 프로젝트에서 왜 필요한가 |
| --- | --- |
| SVG 좌표계와 `viewBox` | 줍스가 어떤 화면 크기에서도 비율을 유지해야 한다 |
| SVG 구조화 (`<g>`, `<defs>`, `<use>`) | 표정 교체가 눈 도형 하나 바꾸는 일이 되려면 구조가 그렇게 짜여 있어야 한다 |
| SVG 그라디언트·필터 | 매끈한 흰 셸의 광택, 바이저 발광. 단 `filter`는 비싸다 |
| CSS 애니메이션 vs JS 애니메이션 | 부유·맥동은 CSS로(컴포지터 스레드), 게임 로직 연동은 JS로 |
| 컴포지팅과 `will-change` | 남용하면 메모리를 먹는다. 언제 쓰는지 |
| `prefers-reduced-motion` | 전정기관 장애가 있는 사용자에게 부유 애니메이션은 불편을 준다 |

**자기 검증 질문**
- 새 표정을 하나 추가하는 데 몇 줄이 필요한가? 몸통 코드를 건드렸다면 구조가 잘못된 것이다
- 애니메이션 추가 후 M1의 프레임률이 유지되는가? 측정했는가?
- `filter: drop-shadow`를 매 프레임 움직이는 요소에 걸면 왜 위험한가?

**참고 키워드**: `viewBox`, `preserveAspectRatio`, `SVG <defs>/<use>`, `@keyframes`, `will-change`, `prefers-reduced-motion`, `Web Animations API`

### M5 — 통신 가능 시간 시스템

**핵심 축**: ② 상태 설계, ⑥ 접근성

| 주제 | 이 프로젝트에서 왜 필요한가 |

| 결정론적 스케줄 생성 | "매일 조금씩 밀리는" 것은 랜덤이 아니라 계산 결과여야 한다. 같은 날짜면 항상 같은 결과 |

- 사용자가 비행기를 타고 시간대를 넘어가면 다음 패스 타임 표시가 어떻게 되는가? 그게 옳은 동작인가?
- 같은 날짜·같은 계정이면 항상 같은 패스 타임이 나오는가?
- 탭을 10분간 백그라운드에 두었다 돌아오면 카운트다운이 맞는가?

**참고 키워드**: `Date` UTC vs 로컬, `Intl.DateTimeFormat`, seeded PRNG, `Notification.requestPermission`, `Service Worker`, `timer throttling`

### M7 — 서버 저장 & 바이럴

**핵심 축**: ② 상태 설계, ⑤ 품질

| 주제 | 이 프로젝트에서 왜 필요한가 |
| --- | --- |
| 서버 상태 vs 클라이언트 상태 | 성격이 완전히 다르다. 같은 도구로 다루면 문제가 생긴다 |
| 데이터 마이그레이션 | 기존 localStorage 유저의 기록을 버리지 않고 계정으로 옮긴다 |
| 인증 흐름 | 첫 진입 장벽을 최소화하면서 계정을 붙이는 방법 |
| Server Actions / API Route | ADR-001에서 미뤄둔 Next.js 서버 기능을 여기서 쓴다 |
| 낙관적 업데이트 | 청소 결과 저장이 네트워크를 타면 UI가 기다려선 안 된다 |
| 공유 링크와 OG 이미지 | 바이럴은 링크가 예쁘게 미리보기되는 것에서 시작한다 |

**자기 검증 질문**
- 저장 요청이 실패하면 사용자의 방금 플레이 결과는 어떻게 되는가?
- 오프라인에서 플레이한 결과는 언제 동기화되는가?
- 기존 localStorage 유저가 로그인했을 때 데이터가 합쳐지는가, 덮어써지는가? 의도한 대로인가?

**참고 키워드**: `Server Actions`, `optimistic update`, `TanStack Query` (개념 참고), `next/og`, 데이터 마이그레이션 전략
